# 02. 데이터 불러오기: useState, useEffect, 커스텀 훅


## 개념 1: useState: 바뀌는 값 기억하기

```js
const [list, setList] = useState([])
```

- 컴포넌트 함수는 화면을 다시 그릴 때마다 처음부터 다시 실행된다. 그래서 일반 변수(`let list = []`)는 매번 초기화된다.
- `useState`로 만든 값은 React가 기억해 준다.
- 값을 바꿀 때는 반드시 `setList(새값)`을 쓴다. 그래야 React가 "바뀌었으니 다시 그려야지" 하고 알아챈다. `list.push(...)`처럼 직접 고치면 화면이 안 바뀐다.

### 초깃값에 함수 넣기
```js
const [list, setList] = useState(() => readListCache(localStorage) ?? [])
```
함수를 넘기면 **처음 한 번만** 실행된다. localStorage를 읽는 작업을 화면을 다시 그릴 때마다 반복하지 않으려고 이렇게 썼다.

`??`는 "왼쪽이 `null`이나 `undefined`면 오른쪽 값을 쓴다"는 뜻이다.

## 개념 2: 상태 3종 세트 — 데이터, 로딩, 오류

```js
const [list, setList] = useState(...)
const [loading, setLoading] = useState(...)
const [error, setError] = useState(null)
```

데이터를 불러오는 화면은 거의 항상 이 세 가지 상태를 가진다. `App.jsx`에서는 상태에 따라 다른 화면을 보여 준다.

```jsx
{loading && <p className="status">불러오는 중…</p>}
{error && ( ...다시 시도 버튼... )}
{!loading && !error && <PokemonGrid pokemonList={list} />}
```

`조건 && <JSX>`는 "조건이 참일 때만 그린다"는 뜻이다. JSX에는 `if`문을 바로 쓸 수 없어서 이 방식을 많이 쓴다.

## 개념 3: useEffect: 화면을 그린 다음에 할 일

```js
useEffect(() => {
  // 화면을 그린 뒤 실행된다
  fetchPokemonList().then(...)

  return () => {
    // 정리(cleanup): 다음 실행 전이나 화면이 사라질 때 실행된다
  }
}, [attempt, list.length])   // ← 의존성 배열
```

- 컴포넌트 함수 본문은 "화면이 어떻게 생겼는지"만 계산해야 한다. 네트워크 요청 같은 바깥 세상과의 작업(**부수 효과**, side effect)은 `useEffect` 안에서 한다.
- **의존성 배열** `[attempt, list.length]`: 이 값들이 바뀔 때만 effect를 다시 실행한다. 빈 배열 `[]`이면 처음 한 번만 실행된다.

### 왜 `ignore` 변수가 있나?
```js
let ignore = false
fetchPokemonList().then((raw) => {
  if (ignore) return     // 이미 정리된 effect의 응답이면 버린다
  ...
})
return () => { ignore = true }
```
요청은 시간이 걸린다. 응답이 오기 전에 effect가 다시 실행되거나 화면이 사라지면, 늦게 온 옛 응답이 화면을 덮어쓸 수 있다. 정리 함수에서 `ignore = true`로 표시해서 그런 응답을 버린다.

개발 모드의 `<StrictMode>`는 실수를 찾으려고 effect를 일부러 **두 번** 실행한다. 그래서 Network 탭에 요청이 두 번 보일 수 있지만, 첫 번째 응답은 `ignore` 때문에 버려진다. 배포용 빌드에서는 한 번만 실행된다.

## 개념 4: 「다시 시도」의 원리

```js
const [attempt, setAttempt] = useState(0)
const retry = () => {
  setError(null)
  setLoading(true)
  setAttempt((n) => n + 1)
}
```
`attempt`는 의존성 배열에 들어 있다. 버튼을 누르면 숫자가 1 늘고, 값이 바뀌었으니 effect가 다시 실행되면서 요청을 새로 보낸다.

**왜 `setLoading(true)`를 effect 안이 아니라 여기서 부르나?** 처음 작성할 때는 effect 맨 앞에서 불렀는데, 린터(`oxlint`)가 경고를 냈다. effect는 화면을 **그린 뒤에** 실행되므로, 그 안에서 바로 상태를 바꾸면 "그림 → 상태 변경 → 또 그림"이 된다. 원인이 된 이벤트(버튼 클릭)에서 상태를 바꾸면 한 번에 그린다. **effect는 바깥 세상과 맞추는 일(요청)에만 쓰고, 사용자 행동에 따른 상태 변경은 이벤트 처리 함수에서 한다**는 원칙을 기억해 두자.

`setAttempt((n) => n + 1)`처럼 함수를 넘기면 "지금 값에서 1 더하기"가 된다. 이전 값을 기준으로 바꿀 때는 이 방식이 안전하다.

## 개념 5: 커스텀 훅

`use`로 시작하는 함수 안에서 `useState`·`useEffect`를 쓰면 그 함수가 **커스텀 훅**이 된다.

```js
// App.jsx: 어떻게 불러오는지는 몰라도 된다
const { list, loading, error, retry } = usePokemonList()
```
불러오기 로직을 `App`에서 떼어 냈더니 `App`은 "무엇을 보여 줄지"에만 집중한다. 같은 목록이 다른 화면에서도 필요하면 훅만 부르면 된다.

**훅의 규칙:** 훅은 컴포넌트나 다른 훅의 **맨 위**에서만 부른다. `if` 안이나 반복문 안에서 부르면 안 된다.

## 역할 나누기

| 폴더 | 하는 일 | 테스트 |
|---|---|---|
| `api/` | 서버와 통신 (`fetch`) | 실제 서버가 필요해서 테스트 안 함 |
| `lib/` | 데이터 변환 (순수 함수) | **테스트함**: 입력이 같으면 결과도 늘 같다 |
| `hooks/` | 상태 + 타이밍 관리 | 브라우저에서 직접 확인 |

`listCache.js`는 `localStorage`를 직접 쓰지 않고 `storage`를 인자로 받는다. 그래서 테스트에서는 가짜 저장소를 넣어 "깨진 값이 들어 있을 때"같이 일부러 만들기 어려운 상황도 검사할 수 있다.

## GraphQL 한 줄 설명

보통 API(REST)는 주소마다 정해진 데이터를 준다. GraphQL은 **원하는 필드를 쿼리로 골라서** 요청한다. PokeAPI의 REST로 한국어 이름을 받으려면 1,025번 요청해야 하지만, GraphQL로는 한 번이면 된다. 쿼리는 `src/api/pokemon.js`의 `LIST_QUERY`에 있다.
